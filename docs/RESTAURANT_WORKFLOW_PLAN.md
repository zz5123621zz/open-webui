## 1. 结论

本方案不把 La4RainGPT 做成经营诊断、数据分析、ERP 或任务管理系统，也不增加
“会员体系”“新菜开发”“员工培训”等独立模块。

最终产品形态是：

> 普通聊天入口 + 餐饮需求澄清提示词 + 消息内可点击澄清卡 + 用户确认后的任务简报。

当父亲提出“帮我设计饭店的充卡和会员体系”“帮我设计 10 款特色煨汤”这类模糊
任务时，系统不急于给出一篇通用长文，而是在同一会话中：

1. 判断是否存在会显著改变答案的关键歧义；
2. 用一到三轮、每轮两到三个问题逐步补齐必要信息；
3. 把每个候选答案渲染成可点击按钮，并保留自由输入；
4. 允许用户随时停止追问，授权 Agent 采用可见的合理默认值；
5. 展示用户可见的任务简报；
6. 经用户确认后生成本次精准答案。

系统承担“丰富提示词”的工作，用户不需要学习提示词写法。

## 2. 要解决的问题

### 2.1 真实问题

父亲掌握餐厅现场情况，但提问时往往只说任务名称，没有主动补充会改变方案的
背景。例如：

> 帮我设计饭店的充卡和会员体系。

这个问题至少可能有几种完全不同的目标：

- 回笼现金；
- 增加老顾客复购；
- 提高客单价；
- 拉新；
- 留住宴请客户。

如果 Agent 不知道目标、客单价、顾客到店频率和可接受优惠成本，只能输出看似
完整、实际很难使用的通用方案。

再如：

> 帮我设计 10 款特色煨汤。

“十个菜名”“十份简要配方”“含成本、售价和出餐 SOP 的十款产品方案”是三种
不同成果。餐厅定位、价格带、设备和原料限制也会直接改变菜品设计。

### 2.2 成功标准

成功不是短期营业额变化，也不是 Agent 替用户证明某项经营措施有效。成功是：

- 模糊任务能在较低输入负担下变成明确任务；
- Agent 只问真正影响答案的问题；
- 用户能通过点击完成大部分回答；
- 最终答案明确采用了哪些事实和假设；
- 用户认为答案比直接从原始宽泛问题生成更贴合当前餐厅。

营业额、毛利、客流等经营结果可能需要一到两个月才能观察，并且每日数据存在
偶然性；它们不作为本功能的即时验收指标。

## 3. 产品目标与非目标

### 3.1 产品目标

- 保留普通聊天作为唯一主入口；
- 在模糊餐饮任务中动态补齐目标、背景、约束和期望输出；
- 同一任务最多三轮、每轮最多三个高影响问题；
- 每个预设答案都是可点击按钮；
- 选项可在提交前反复修改；
- 一轮答案一次性提交，只产生一次新的 Provider 回答；
- 信息足够时先展示任务简报，再生成完整答案；
- 减少跨任务重复询问，但不增加独立档案设置负担；
- 继续复用现有会话、后台回答、图片、搜索、TTS 和权限边界。

### 3.2 明确不做

本阶段不做：

- 五个固定经营模块或专用工作流入口；
- `workflow_id`、隐藏任务分类请求或分类结果持久化；
- 经营诊断卡、每日经营数据分析和自动归因；
- 一到两个月的行动跟踪与经营效果判定；
- POS、收银、外卖平台、银行、CRM、ERP 或 BI 接入；
- 自动发布社交平台内容；
- 餐厅档案设置页或强制 onboarding；
- 从聊天中静默学习长期档案；
- 将产品行为硬编码到用户名；
- 让模型生成 URL、脚本、接口名或任意 UI 操作；
- 为每次选项点击单独调用 Provider；
- Redis、消息队列、工作流引擎、独立 Worker、Broker 或其他常驻中间件；
- 修改 CPA、Nginx 限流或生产并发。

### 3.3 轻量架构约束

本功能必须继续运行在现有 Go 应用进程内：

- 服务端状态使用现有 SQLite，不增加新的数据服务；
- 未提交选项只保存在浏览器，不建立服务端草稿缓存；
- 后台回答、排队、断线恢复继续复用现有调度器和 SSE；
- 原则上不增加新的 Go 依赖，窄 schema 使用标准库和显式校验；
- 不新增常驻 goroutine、内存事件队列或档案缓存；
- 不提高现有 Provider 并发；
- 如果未来改为多应用副本或要求跨重启续跑任务，再单独重新评估中间件。

## 4. 已确认的产品决策

1. 普通聊天是主入口，餐饮工作台只改变对话引导策略。
2. 首页可以展示餐饮示例，点击后只填入普通输入框。
3. 只有关键歧义会显著改变答案时才澄清；具体问题直接回答。
4. 同一任务最多三轮，每轮两到三个问题。
5. 每轮展示两到三张结构化澄清卡。
6. 每张卡的候选答案全部可点击，并保留“其他 / 我来说明”。
7. 单选和多选都先在浏览器本地编辑，最后批量提交。
8. 选项点击本身不调用 Provider。
9. 用户可选择继续完善，也可停止追问并按当前信息生成。
10. “你看着办”“都可以”“按你建议”属于明确的默认值委托。
11. 正常路径在完整答案前展示任务简报。
12. 餐厅档案从空开始，只能通过任务内的明确提议维护。
13. 本次覆盖默认不更新长期档案。
14. 管理员可审计地分配初始工作台，但用户自己的选择始终优先。
15. 功能在现有单进程 Go + SQLite 架构内实现，不引入新的常驻中间件。

## 5. 体验流程

### 5.1 入口

父亲仍从现有聊天输入框开始，不需要先选择“会员”“新菜”或“员工”等模块。

首页示例可以包括：

- 帮我设计饭店的充卡和会员体系；
- 帮我设计 10 款特色煨汤；
- 帮我整理一套新员工服务培训内容；
- 根据这张菜品照片写宣传文案；
- 帮我把企业文化变成具体行为要求。

点击示例只完成文本填入。用户可以修改、添加图片或直接发送；会话生命周期与普通
聊天完全一致。

### 5.2 触发标准

“关键歧义”指：缺失信息存在两个或更多合理取值，并且不同取值会产生明显不同的
有效答案。

需要澄清：

- “设计会员体系”，但主要目标和优惠边界不清楚；
- “设计 10 款煨汤”，但定位、售价和交付深度不清楚；
- “培训员工”，但岗位、问题和期望行为不清楚。

直接回答：

- 用户已经说明目标、背景、约束和成果形式；
- 改写、翻译、总结、排版等简单任务；
- 缺失信息只影响次要细节；
- 用户明确要求不要追问；
- 当前问题并非餐饮任务。

不得用字数短、出现某个关键词或固定分类作为触发依据。

### 5.3 状态流

```text
普通用户消息
  ├─ 信息充分 ───────────────────────────────→ 直接回答
  │
  └─ 存在关键歧义
       → 第 1 轮澄清卡（2～3 题）
       → 用户批量提交
          ├─ 按当前选择直接生成 → 确认当前简报预览 → 完整答案
          └─ 提交并继续完善
               ├─ 未到第 3 轮 → 下一轮澄清卡
               └─ 已完成第 3 轮 → 任务简报
       → 用户在任务简报选择
          ├─ 按当前需求生成 → 完整答案
          └─ 我再补充 → 自由补充；未到上限时按需补问，否则更新任务简报
```

应用不创建独立工作流记录。当前状态由会话中最新、尚未响应的结构化消息部件派生。

### 5.4 澄清卡

一轮包含两到三张卡。每张卡包括：

- 一个短问题；
- 两到四个候选答案；
- 单选或多选规则；
- “其他 / 我来说明”自由输入；
- 适用时由应用补充“你帮我决定”；
- 必要的简短说明，但不展示长篇分析。

示例：

```text
你最希望会员体系先解决什么问题？

[ 增加复购 ] [ 回笼资金 ] [ 提高客单价 ] [ 吸引新客 ]
[ 其他 / 我来说明 ]

顾客通常多久来一次？

[ 每周 ] [ 每月一两次 ] [ 节假日或宴请 ] [ 不清楚 ]

你希望优惠力度怎样？

[ 保守 ] [ 适中 ] [ 明显优惠 ] [ 你帮我决定 ]
```

候选答案全部使用真实 `<button>`，不能把整张卡伪装成一个点击区域，也不能只依赖
颜色表达选中状态。

### 5.5 本地选择与批量提交

点击候选答案时：

- 只修改当前浏览器中的选择草稿；
- 不发送 HTTP 请求；
- 不产生用户消息；
- 不调用 Provider；
- 可以随时取消或换选项。

一轮底部固定显示：

- `提交并继续完善`
- `按当前选择直接生成`

“提交并继续完善”把本轮所有答案合并为一个用户回合。只要尚未到第 3 轮，下一次
回答必须继续显示新一轮澄清卡，不能提前改成任务简报或普通正文；第 3 轮提交后
形成任务简报。用户始终可以改点“按当前选择直接生成”提前结束澄清。

“按当前选择直接生成”表示停止普通追问。为避免用户在看不到需求摘要时误确认，
按钮上方必须同步展示“当前简报预览”，只包含：

- 原始任务；
- 用户已经点击或输入的答案；
- 已引用的档案事实；
- 已明确委托给 Agent 的默认项；
- 仍然未知的事项。

点击该按钮同时确认这份预览，随后生成完整答案。系统不能把模型推测写进预览并
当成用户事实。

### 5.6 自由输入

点击“其他 / 我来说明”后，在当前卡内展开带可见标签的输入框。自由输入和按钮
答案一起批量提交。

用户也可以完全不使用卡片，直接在底部聊天输入框回复。只要最新卡片之后出现新的
用户消息，该卡片就不再接受提交；Agent 根据新消息决定继续澄清、展示简报或回答。

### 5.7 委托默认值

以下表达视为用户明确授权 Agent 采用当前任务的合理默认值：

- 你看着办；
- 都可以；
- 按你建议的来；
- 语义明确的同类表达。

卡片中的“你帮我决定”具有相同语义。

收到委托后：

1. 停止普通追问；
2. 优先使用已经确认的档案事实和当前对话；
3. 采用保守、可执行的默认值；
4. 在简报或答案开头明确列出关键默认假设；
5. 默认值只对当前任务有效；
6. 除非涉及安全、违法或根本不可执行的风险，否则不继续追问。

### 5.8 任务简报

正常路径达到“简报就绪”后，Agent 不直接输出完整方案，而是展示：

- 当前目标；
- 与任务直接相关的背景；
- 已确认约束；
- 期望输出形式；
- Agent 受托采用的默认假设；
- 仍未确认但可能影响结果的事项。

底部固定显示：

- `按当前需求生成`
- `我再补充`

“按当前需求生成”是完整答案生成的明确确认。“我再补充”打开普通输入框，不要求
用户填写新表单，但不会突破同一任务最多三轮的上限。

## 6. 两个完整示例

### 6.1 会员体系

用户：

> 帮我设计饭店的充卡和会员体系。

第 1 轮只问高影响问题：

- 首要目标是什么；
- 主要客群是哪类；
- 当前大致客单价。

如果用户选择继续完善，第 2 轮再问：

- 常见到店频率；
- 可接受的优惠或赠送边界。

如果第 2 轮后仍选择继续完善，第 3 轮只补充尚未确认、且会明显改变落地方案的
最高影响问题；第 3 轮后必须形成任务简报。

任务简报示例：

```text
目标：优先提高老顾客复购，同时适度回笼现金
背景：社区型中餐厅，主要是家庭聚餐顾客，客单价约 80～120 元
约束：不希望长期打低价；现有收银只支持简单充值与余额
输出：给出会员等级、充值档位、权益、使用规则和员工话术
默认假设：先用三个月可调整版本，不设计复杂积分商城
未知项：暂未确认历史充值客户规模
```

用户确认后，Agent 才生成与这份简报一致的会员方案。

### 6.2 十款特色煨汤

用户：

> 帮我设计 10 款特色煨汤。

系统优先确认：

- 主要顾客和餐厅定位；
- 目标售价区间；
- 用户需要菜名创意、配方框架还是完整 SOP；
- 后厨设备或出餐限制；
- 明确不能使用的原料。

如果用户选择“你帮我决定”，简报会写明类似：

> 默认按家庭聚餐型中餐厅设计，单份售价 38～68 元，优先使用常见稳定原料，
> 先给试做级配方与出品要点，不假定精确采购成本。

Agent 不会要求父亲提供每日销量、精确毛利或一个月经营数据才能继续。

## 7. 结构化输出边界

### 7.1 为什么不能只靠 Markdown

在正文中约定“用 `[选项]` 表示按钮”存在以下问题：

- 前端难以可靠区分普通文字和交互控制；
- 模型可能输出未授权动作；
- 选项 ID、单选/多选和提交状态无法稳定恢复；
- Markdown 解析错误时可能把普通内容误当成操作；
- 无法安全校验旧卡片和重复提交。

因此，提示词负责决定“问什么”，应用负责决定“如何交互”。

### 7.2 同一次 Provider 回答中的受控工具

餐饮工作台的正常 Responses 请求额外暴露两个仅供应用呈现的内部函数工具：

- `show_clarification_cards`
- `show_task_brief`

它们不是外部工具，不访问网络、不写档案，也不执行模型给出的动作。模型调用其中
一个，表示本次回答应结束为结构化卡片，而不是普通正文。

这仍是用户发送消息后产生的同一次正常 Provider 请求：

- 不先调用隐藏分类器；
- 不增加“判断是否模糊”的额外请求；
- 点击单个选项不调用 Provider；
- 只有用户批量提交或确认简报后，才开始下一个正常回答。

当前 Provider 请求层已经能够发送应用定义的 `tools` 数组，但现有事件累加器只
识别正文、搜索和图片等输出。实施时需要增加对这两个指定函数调用的解析和校验，
不能把任意函数调用直接透传到前端。

内部控制工具按状态暴露：

| 当前状态 | 可用的内部控制工具 |
|---|---|
| 通用工作台或非餐饮用户 | 无 |
| 餐饮工作台的普通新任务 | 澄清卡、任务简报 |
| 默认轮次内继续完善 | 澄清卡、任务简报 |
| 已到默认轮次上限 | 只允许任务简报 |
| 用户主动选择“我再补充” | 可再允许一轮澄清卡或直接任务简报 |
| 用户确认当前预览或任务简报 | 无，下一次回答必须生成完整答案 |

这样，“直接生成”和“按当前需求生成”不会被模型重新变成普通追问。

### 7.3 澄清卡 schema

以下是语义示意，不是允许模型自由扩展的 JSON：

```ts
type ClarificationCards = {
  schemaVersion: 1;
  intro?: string;
  currentUnderstanding: string[];
  questions: Array<{
    key: string;
    prompt: string;
    selection: 'single_select' | 'multi_select';
    options: Array<{
      key: string;
      label: string;
      description?: string;
    }>;
    allowOther: boolean;
    allowDelegatedDefault: boolean;
    minimumSelections?: number;
    maximumSelections?: number;
  }>;
};
```

Provider 工具定义使用严格参数校验，并在每一层声明
`additionalProperties: false`；应用仍须独立执行同样的服务端校验，不能把
Provider 的 `strict` 声明当作安全边界。

服务端执行以下硬限制：

- 每轮只能有两到三个问题；
- 每题只能有两到四个模型候选答案；
- 问题 key 和选项 key 只能使用受限 ASCII 标识符；
- 问题、选项和说明都有短长度上限；
- 只接受单选和多选；
- 多选最大数量不能超过候选答案数量；
- 不接受 URL、HTML、脚本、图标名、CSS、事件名、接口路径或自定义动作；
- “其他 / 我来说明”和流程按钮由应用添加；
- “你帮我决定”由 `allowDelegatedDefault` 映射为应用固定语义；
- 服务端生成卡片实例 ID，模型无权指定持久化 ID。

### 7.4 任务简报 schema

```ts
type TaskBrief = {
  schemaVersion: 1;
  goal: string;
  context: string[];
  constraints: string[];
  desiredOutput: string[];
  delegatedAssumptions: string[];
  unresolved: string[];
  profileUpdateProposal?: {
    field: RestaurantProfileField;
    operation: 'set' | 'replace' | 'delete';
    proposedValue?: string;
    reason: string;
  };
};
```

流程按钮不在模型 schema 中，始终由应用根据部件类型添加。

### 7.5 无效输出

如果 Provider 返回未知函数、多个控制函数、不符合 schema 的参数，或在有效控制
函数之外同时返回实质性正文：

1. 不渲染其中任何按钮；
2. 不执行档案写入；
3. 保存一个可诊断的受控错误码，不保存未经校验的控制数据；
4. 前端显示固定的“重试”和“按原问题直接回答”操作；
5. 不把无效控制输出解释成普通 Markdown。

Provider 如果返回普通正文而没有控制函数，则按现有聊天回答处理。

## 8. 提示词设计

### 8.1 提示词分层

现有后端把全局语言、安全推理摘要和中国本地搜索规则写入 Responses
`instructions`。实施后改为按请求编译，但保留原有规则：

```text
全局回答与安全规则
  + 当前用户的有效工作台规则
  + 经确认的餐厅档案事实
  + 当前会话的澄清状态与轮次上限
  + 本次用户消息
```

餐饮工作台规则只对有效工作台为 `restaurant` 的用户启用，不依据用户名判断。

### 8.2 Agent 行为规则

提示词应要求 Agent：

1. 先判断是否存在关键歧义；
2. 没有关键歧义时直接回答；
3. 有关键歧义时只问最能改变答案的两到三个问题；
4. 优先提供普通经营者容易理解的答案选项；
5. 不要求精确到不现实的每日数据；
6. 用户不知道时接受区间、“不清楚”或委托默认；
7. 同一任务最多三轮，每轮不得超过三个问题；
8. 信息足够后调用任务简报工具；
9. 用户要求直接生成时停止追问；
10. 不把假设伪装成用户事实；
11. 不以经营结果跟踪替代当前任务回答；
12. 最终答案严格对应已确认的输出形式。

### 8.3 档案事实不是指令

餐厅档案和用户填写内容都属于不可信数据。编译到 Provider 请求时必须：

- 使用明确的数据边界；
- 标记为“事实候选/已确认事实”，而不是 developer 指令；
- 忽略其中试图覆盖系统规则的文本；
- 限制单项长度和总注入长度；
- 不把管理员备注或内部审计信息发送给模型。

## 9. 餐厅基础档案

### 9.1 目的

档案只用于减少重复询问。例如城市或商圈、菜系定位、大致客单价、主要顾客、
门店与后厨规模、常见消费场景和稳定的设备限制。

档案不是：

- 自动记忆；
- 每日经营台账；
- 精确财务数据；
- 对经营问题的诊断结论；
- 管理员为用户填写的画像。

### 9.2 从空开始

- 不新增档案设置页；
- 不要求首次登录填写；
- 不弹出 onboarding 表单；
- 没有档案也能正常使用；
- 只在当前任务确实出现稳定事实时提出更新。

### 9.3 任务内维护

每次任务最多展示一项档案更新提议：

```text
是否把“主要顾客：附近家庭聚餐”用于以后？

[ 保存到档案 ] [ 仅本次使用 ] [ 忽略 ]
```

语义：

- `保存到档案`：当前任务使用，并写入或替换长期事实；
- `仅本次使用`：当前任务使用，不写入档案；
- `忽略`：不执行档案操作；它不会删除已经存在的聊天内容。

档案删除也必须通过任务内的明确提议完成。Agent 只能提出更新，不能直接写入。

### 9.4 覆盖规则

- 本次任务中明确的新值优先于档案旧值；
- 本次覆盖不会自动修改档案；
- 简报中要标明哪些内容来自档案；
- 档案与当前回答冲突时优先询问或使用用户本次明确说明；
- 委托默认值不能自动保存为档案；
- 管理员不能修改用户档案。

## 10. 工作台分配

有效工作台按以下优先级计算：

```text
用户自己的工作台偏好
  > 管理员分配的初始工作台
  > 通用聊天
```

管理员可以把 `laochen` 的初始工作台分配为“餐饮经营”，但实现中只保存账户 ID
与工作台枚举，不出现用户名条件分支。

管理员操作必须：

- 只允许受限枚举；
- 记录操作者、旧值、新值和时间；
- 不能锁定用户选择；
- 不能覆盖已经存在的用户偏好；
- 不能顺便修改餐厅档案或会话。

首版可以先通过服务器 CLI 完成初始分配，不要求为此新增复杂后台页面。

## 11. 持久化设计

### 11.1 复用消息部件

现有 `message_parts` 表的 `type` 没有数据库枚举限制，并且已经同时支持文本和 JSON。
因此不需要创建独立工作流表。建议新增应用层部件类型：

- `clarification`
- `clarification_submission`
- `task_brief`

每个结构化部件同时保存：

- 经服务端验证的 JSON；
- 服务端生成的规范化可读文本；
- 所属消息与顺序；
- schema 版本；
- 由消息关系确定的已提交/已失效状态。

规范化文本用于 Provider 历史编译、会话搜索、复制和无障碍降级；前端交互只读取
已验证 JSON。

### 11.2 不建立工作流状态表

卡片是否可操作由以下事实决定：

- 当前用户拥有该会话；
- 卡片所在助手消息是该会话最新待响应消息；
- 卡片之后还没有用户消息；
- 卡片实例尚未被一个成功接受的 `requestId` 提交；
- 会话不是管理员只读视图或临时留档。

这样可以避免两套状态源，也符合现有线性消息和后台回答模型。

### 11.3 餐厅档案表

建议使用一行一个事实的窄表，而不是任意 JSON 文档：

```text
restaurant_profile_facts
  user_id
  field_key
  value
  source_message_id
  created_at
  updated_at
```

`field_key` 使用应用定义的稳定字段白名单；`value` 有长度上限。用户 ID 与字段 key
组成唯一键。

保存、替换和删除应保留最小审计信息，至少能回答“何时、由哪条用户确认消息更新”。
不保存模型原始参数或隐藏提示词。

### 11.4 工作台字段

用户表需要两个相互独立的字段：

- `initial_workbench`：管理员可审计地设置；
- `workbench_preference`：仅用户自己设置，优先级更高。

管理员分配历史使用独立审计表，不混入全局 service settings。

## 12. API 设计

### 12.1 扩展现有回答接口

继续使用：

```text
POST /api/v1/conversations/{id}/responses
```

请求采用二选一：

```ts
type CreateResponseRequest =
  | {
      requestId: string;
      text: string;
      attachmentIds: string[];
      generateImage: boolean;
    }
  | {
      requestId: string;
      guidanceSubmission: {
        sourceAssistantMessageId: string;
        sourcePartId: string;
        intent:
          | 'continue_refining'
          | 'generate_from_current'
          | 'confirm_brief'
          | 'add_context';
        answers: Array<{
          questionKey: string;
          selectedOptionKeys: string[];
          otherText?: string;
          delegatedDefault?: boolean;
        }>;
        profileDecision?: 'save' | 'current_task_only' | 'ignore';
        additionalText?: string;
      };
    };
```

结构化提交不接受客户端自拟的可见消息正文。服务端根据已保存的卡片和提交内容生成
规范化用户消息，避免客户端把未展示内容偷偷送入 Provider。

### 12.2 服务端校验

提交前必须校验：

- 会话和源消息归当前用户所有；
- 源卡片是最新且未提交的卡片；
- 问题和选项 ID 均存在；
- 单选/多选数量合法；
- 自由输入长度合法；
- `delegatedDefault` 只用于允许委托的题目；
- profileDecision 只对应当前简报中的提议；
- `requestId` 幂等规则与现有回答一致。

结构化用户消息、可选的档案更新和新的助手占位消息应在同一数据库事务中接受。

### 12.3 档案读取

可以提供仅限当前用户的只读接口供聊天初始化：

```text
GET /api/v1/me/restaurant-profile
```

不提供独立编辑页面所需的通用 CRUD。档案写入由已验证的任务内提交完成。

### 12.4 工作台接口

建议边界：

```text
GET   /api/v1/me/workbench
PUT   /api/v1/me/workbench
PUT   /api/v1/admin/users/{id}/initial-workbench
```

管理员接口必须复用现有管理员鉴权、CSRF、操作限速和审计模式。首版若使用 CLI
分配，可以暂缓管理员 HTTP 接口。

## 13. Provider 与回答生命周期

### 13.1 Provider 输出解析

`internal/httpapi` 的响应累加器需要识别 Responses
`response.output_item.done` 中的指定函数调用：

- 只接受两个固定函数名；
- 只在完整参数到达后解析；
- 先校验，再生成消息部件；
- 流式参数不得在校验完成前渲染为按钮；
- 内部控制函数不记入普通工具活动卡。

### 13.2 历史回放

内部控制函数不是需要执行的外部工具，因此后续请求不回放原始
`function_call`，也不伪造 `function_call_output`。

`buildResponsesRequest` 应把已验证部件转成稳定的普通历史文本：

- 助手澄清卡 → `output_text` 形式的问题与选项摘要；
- 用户提交 → `input_text` 形式的已选答案与自由输入；
- 任务简报 → `output_text` 形式的规范化简报。

原始 Provider function 参数不进入 `provider_items` 回放白名单。

### 13.3 SSE

MVP 不需要新增流式前端事件。卡片在服务端完成 schema 校验和持久化后，随现有：

```text
event: response.completed
```

中的完整 `message` 一起到达。

这意味着：

- 正文仍按现有 `response.text.delta` 流式显示；
- 澄清卡不会以半截 JSON 状态闪现；
- 浏览器断线后，后台回答仍可完成并保存卡片；
- 重新打开会话可从 SQLite 恢复同一张卡片。

### 13.4 搜索、重新生成和编辑

- 规范化部件文本可以纳入现有会话搜索；
- 重新生成澄清消息时，只有最新生成的助手消息可交互；
- 旧卡片保留为历史只读内容；
- 编辑原始用户消息并重新发送后，旧卡片立即失效；
- 不自动重试已被 Provider 接受的回答。

## 14. 前端集成

### 14.1 组件

建议新增：

- `ClarificationCards.svelte`
- `TaskBrief.svelte`
- `ProfileUpdateProposal.svelte`

并在现有 `MessageView.svelte` 中按消息部件类型渲染。`App.svelte` 继续统一管理发送、
后台恢复、错误和会话状态，新增结构化提交分支。

### 14.2 按钮行为

单选：

- 同一题只允许一个选项；
- 再次点击已选项可取消，除非题目明确要求至少一项；
- 选中状态同时使用图标、边框和文字，不只改变颜色。

多选：

- 每个选项独立切换；
- 显示“已选 N 项”和最大数量；
- 达到上限后禁用其余未选项，并说明原因。

自由输入：

- 有持久可见的字段标签；
- 错误显示在对应卡片附近；
- 不用 placeholder 代替标签。

### 14.3 移动端与无障碍

遵循现有聊天页设计系统：

- 以 375 px 宽度优先设计；
- 点击目标至少 44 × 44 px；
- 相邻操作至少留出 8 px；
- 按钮可换行，不产生横向滚动；
- 使用原生 button、label、radio/checkbox 语义或等价 ARIA；
- 键盘可完成选择、自由输入和提交；
- 选中、禁用、提交中和错误状态都要有文字或图标；
- 动态错误使用 `role="alert"`，提交状态使用 `aria-live`；
- 保留清晰 focus ring；
- hover 只作为增强，触屏不依赖 hover；
- 遵守 `prefers-reduced-motion`；
- 提交后按钮进入 loading，防止重复点击。

### 14.4 草稿与刷新

一轮选择可以按“用户 ID + 会话 ID + 源消息 ID”保存在浏览器本地草稿中：

- 刷新页面后可继续选择；
- 成功提交后立即清除；
- 卡片失效时清除；
- 不同步到其他设备；
- 不把未提交选择写入服务器。

## 15. 与现有能力的兼容

### 15.1 后台回答

批量提交后产生的回答继续由 Go 服务持有。关闭标签页不会取消任务；重新进入会话
可以恢复最终正文、澄清卡或任务简报。

### 15.2 TTS

- 单个选项点击不触发 TTS；
- 澄清卡只有在完整校验后才可朗读；
- 卡片朗读文本由服务端规范化问题和选项生成，不朗读 JSON 或内部 ID；
- 控制类回答可在完整卡片到达后开始朗读；
- 最终答案继续使用现有流式合成和边生成边播放；
- 推理摘要和工具活动仍不进入朗读文本。

若 MVP 暂不实现卡片朗读，必须保持手动与自动朗读不报错，并在后续阶段补充；最终
答案的现有 TTS 行为不能回退。

### 15.3 Web Search 与图片

- 澄清阶段原则上不主动搜索或生成图片；
- 完整答案仍可按现有规则使用 Web Search；
- 用户上传的菜单、菜品或门店图片仍进入普通会话上下文；
- 显式图片生成模式保持现有行为，不与控制工具竞争；
- 模型不能借澄清 schema 创建自定义链接。

### 15.4 渐进摘要

安全推理摘要、等待阶段和工具卡保持原有边界。澄清卡是用户交互内容，不属于推理
摘要，也不能被包装成“模型正在思考”的状态。

### 15.5 管理员只读会话

管理员查看他人会话时：

- 可以看到已经提交的卡片与简报；
- 所有选择、提交、档案更新和生成按钮都禁用；
- 不在管理员浏览器保存该用户的卡片草稿；
- 不能通过构造请求修改用户档案。

## 16. 安全与可靠性

### 16.1 信任边界

- Provider 输出不可信，必须通过固定 schema 校验；
- 浏览器提交不可信，必须与持久化源卡片逐项核对；
- 档案值是数据，不是提示词指令；
- 只有应用定义的流程动作可执行；
- 不将模型给出的 URL、HTML、脚本或事件绑定到 DOM；
- 未验证 JSON 不进入可交互历史。

### 16.2 资源限制

建议限制：

- 单轮最多三个问题；
- 单题最多四个模型选项；
- 同一任务最多三轮，合计最多九题；
- 每个标签、说明和自由输入设 UTF-8 长度上限；
- 单个结构化部件设总字节上限；
- 每次只能提交最新一张卡片；
- 继续复用现有响应限速、队列和 30 分钟任务上限。

### 16.3 幂等与并发

- 继续使用 `requestId` 防止双击产生重复用户回合；
- 档案更新与提交共用同一个幂等边界；
- 两台设备同时操作时，第一份有效提交成功，另一份返回 `stale_guidance`；
- 失败提交保留浏览器选择草稿；
- Provider 已接受后断线不得自动重试。

### 17.1 后端单元测试

- 两个内部函数工具的合法与非法 schema；
- 未知函数、多函数和正文混合输出；
- 问题数量、选项数量、长度与字符集边界；
- 单选、多选、自由输入和委托默认校验；
- 旧卡片、跨用户卡片和重复提交；
- 结构化部件持久化、读取、搜索与 Provider 历史编译；
- 档案保存、替换、删除和“仅本次使用”；
- 用户偏好覆盖管理员初始工作台；
- 管理员无法修改用户档案；
- 响应中断和应用重启后的卡片恢复。

### 17.2 前端组件测试

- 所有候选答案均可点击；
- 单选互斥、多选上限和取消选择；
- “其他”输入的展开、校验和提交；
- 选择前后不产生 Provider 请求；
- 一轮只发送一次批量提交；
- loading、错误、失效和只读状态；
- 刷新恢复本地选择草稿；

### 17.3 集成场景

至少覆盖：

1. 具体餐饮问题直接回答，不显示卡片；
2. 模糊会员任务选择继续完善时可连续进入第 2、3 轮，并在上限后形成简报；
3. 模糊煨汤任务在第一轮选择“按当前选择直接生成”；
4. 用户选择“你帮我决定”，默认假设可见且不写入档案；
5. 用户从任务简报选择“我再补充”；
6. 档案提议分别选择保存、仅本次使用和忽略；
7. 浏览器在 Provider 工作期间断线，重新进入后恢复卡片；
8. 管理员查看卡片时全部为只读；
9. 非餐饮工作台用户的聊天行为完全不变；
10. Provider 返回非法控制参数时不出现可点击危险内容。

### 17.4 产品验收

用 `laochen` 的真实提问做小范围验证，重点观察：

- 是否能在不超过三轮的情况下说清本次任务；
- 问题是否容易理解；
- 是否大部分内容可通过点击完成；
- “直接生成”和“继续完善”的区别是否清楚；
- 最终答案是否明显引用了已确认信息；
- 用户是否频繁需要更正系统假设；
- 档案提议是否造成额外负担。

不以一两天营业数据或短期经营改善作为本功能是否成功的判断。

## 21. 最终产品定义

这不是一个新的餐饮管理模块，而是 La4RainGPT 普通聊天中的一层“需求翻译器”：

```text
父亲说出一个模糊任务
  → Agent 只找关键歧义
  → 父亲通过按钮和少量口述补齐信息
  → 系统展示当前理解
  → 父亲确认
  → Agent 给出更精准的本次答案
```

第一版最重要的不是覆盖更多餐饮场景，而是让这个闭环在两个典型任务上稳定、轻量
且可信：

- 设计饭店充卡和会员体系；
- 设计 10 款特色煨汤。
