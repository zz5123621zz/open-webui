# 后台回答

## 用户可见语义

La4RainGPT 接受回答请求后，回答任务由服务端持有。浏览器 SSE 只是当前页面的
临时订阅：

- 关闭标签页、切换网络、锁屏、刷新或退出登录都不会取消 CPA 请求；
- 用户点击“停止”才会发送经过身份校验的显式取消；
- 再次打开仍在生成的会话时，页面显示“回答正在服务器后台继续生成”，沿用
  原始开始时间，并恢复已保存的推理摘要、正文、工具阶段和图片阶段；
- 页面恢复期间每秒只读取当前 assistant 记录，不重复拉取整段会话；
- 完成后，最终记录替换运行中快照，正常进入聊天历史。

排队阶段使用客户端 `requestId` 作为取消句柄；创建 assistant 后改用消息 ID。
因此“停止”在 CPA 请求开始前后都有效。取消句柄只存在于当前应用进程，并且
只能由创建任务的用户调用。

## 持久化与安全边界

assistant 消息同时承担轻量任务记录：

- `pending` / `streaming` 表示仍在运行；
- `completed` 表示完整结束；
- `interrupted` + `response_cancelled` 表示用户停止；
- `interrupted` + `service_interrupted` 表示应用停止或重启；
- `interrupted` + `response_timeout` 表示超过 30 分钟硬上限。

Provider 产生第一份用户可见证据后立即保存，之后至多每秒替换一次 SQLite
快照。快照只包含允许进入历史的安全推理摘要、正文、经过清洗的工具证据、
引用、生成图片引用和用量；不保存私有思维链、认证信息或任意上游原始事件。

应用正常关机时会取消任务、等待最终状态落库，再关闭 HTTP 服务。若进程被
强制终止，下一次应用服务启动会把遗留的 `pending` / `streaming` assistant
标成 `service_interrupted`，保留最后快照。

服务重启后不会自动重新发送 CPA 请求。已被 Provider 接受的请求可能已经
消耗额度、执行网页搜索或产生其他副作用；自动重发会违反“一次接受、一次
尝试”的边界。用户可以查看保留内容后手动重试。

## 资源模型

实现不增加 Redis、消息队列、WebSocket broker 或常驻 worker 容器。任务仍在
现有 Go 进程和既有并发调度器中运行：

- 每用户最多 2 个、全应用最多 4 个回答；
- 每个任务只增加一个服务端 context、取消句柄和现有响应累积器；
- SQLite 写入频率最多约为每个活跃回答每秒一次；
- 恢复页面每秒读取单条消息。

因此额外常驻内存接近零；主要内存仍是最多四个本来就存在的 Provider 响应
缓冲。长回答会增加 SQLite 写入和 WAL 活动，但不会产生第二份常驻事件回放
队列。

## 运维验证

发布后至少验证：

1. 发送一个会暂停数秒的回答，收到部分正文后关闭浏览器连接；
2. 确认 CPA 只有一次请求，数据库仍为 `streaming` 且部分正文可读；
3. 重新打开会话，确认后台状态、计时和部分内容出现；
4. 确认最终状态为 `completed`；
5. 再启动一个回答并点击“停止”，确认状态为
   `interrupted/response_cancelled`；
6. 在测试回答运行时重启应用，确认保存内容保留且状态为
   `interrupted/service_interrupted`，CPA 没有自动重发；
7. 检查应用 restart count、OOM、SQLite lock 日志和内存峰值。
